# Onboarding a service

`vgate init --service <svc>` writes the skeleton of `<svc-dir>`. Two reference services in the vgate repository
(`https://github.com/benebobaa/vgate/tree/main/services/`) show complete ones; copy the shape of the one closer to
yours, never its values:

- `example-orders`: REST with an API key, PostgreSQL assertions, compose dependencies (Redis, Kafka, a stubbed
  payment provider behind Toxiproxy), event and cache checks.
- `example`: REST verbs with query parameters, a static API key, a cookie-session console login, a streaming
  endpoint, a signed webhook, no envelope, UTC datetimes, no database (state checked through the API), no Docker.

## Files

| File | Purpose |
|---|---|
| `openapi.yaml` | The backend's contract at the synced commit, LF line endings. The approved behaviour. |
| `service.yaml` | Rules, coverage exclusions, Schemathesis settings, environments, dependencies, webhooks. |
| `stack.sh` | `up` (start, wait until healthy, seed a fresh database's test users; idempotent), `down` (stop, keep data), `status` (including the running build), `reset`. |
| `support/fixtures.ts` | The framework's `test`, typed by the contract and extended with the service's fixtures. |
| `generated/openapi.ts` | Types from the contract, generated by `vgate doctor --fix` and the gate; not committed. |
| `inventory.yaml` | The test plan. |
| `FINDINGS.md` | Mismatches between the backend and its spec. |
| `known-failures.yaml` | Optional, human-only: failures the gate tolerates until a date. |

## service.yaml

```yaml
name: <svc>
spec: openapi.yaml
backend:
  repo: ../..                    # the backend in this repository; a separate checkout: ${<SVC>_REPO:-../path}
  contract: openapi.yaml         # the contract's path inside the backend repository
  syncedCommit: <short sha>

rules:
  envelope:            # only if responses share an envelope such as { code, message, data }
    codeField: code
    dataField: data
    successCode: <code of a success>
    codePattern: '<regex that finds codes in response descriptions>'
  datetimeOffset: 'Z'               # only if a source fixes the offset
  strictResponseProperties: true    # undocumented response fields fail the gate
  headers:                          # each with a comment naming its source
    always: { X-Request-Id: '/regex/' }
    withBody: { Content-Type: application/json }
    cors: { Access-Control-Allow-Origin: '{origin}' }
    onStatus: { '401': { WWW-Authenticate: '/^Bearer/' } }
  streaming:                        # only for text/event-stream operations
    terminal: [{ data: '[DONE]' }]

coverage:
  exclude:             # documented pairs out of black-box reach, each with a reason a reviewer can check
    - { code: <code>, reason: <why> }

schemathesis:
  readOnlyMethods: [GET]                                        # REST: the reads
  readOnlyPaths: '<regex of operations that write nothing>'     # e.g. '/search$' for an API that reads through POST
  users: [<seeded users to run as, one may be anonymous>]

environments:
  local:
    disposable: true   # reset, fault injection, stubs and fuzzing allowed
    baseUrl: http://localhost:8080
    healthPath: /health
    origin: http://localhost:3001       # sent on every call: CORS is checked, Origin-based CSRF guards pass
    auth: { header: X-Api-Key, scheme: '' }   # only for a non-Bearer credential; default Authorization / Bearer
    db: { url: 'postgres://app:app@${STACK_HOST:-localhost}:5432/app', schema: public }
    compose: { file: compose.yaml, project: <svc> }
    users:
      <name>: { token: '${<SVC>_TOKEN}', role: ... } # a static bearer token or API key
      <name>: { username: ..., password: ..., role: ... } # a session or Keycloak login (below)
```

Leave out what the service does not have. Container URLs use `${STACK_HOST:-localhost}` so the same file works in CI,
where published ports may answer on another host. Secrets of shared environments come from environment variables
(`${VAR}` without a default fails loudly), never from the file; only `local` carries local-only defaults.

How users log in, beyond static credentials (vgate docs):

- **Cookie session** (console APIs): `auth.session` names the login operation, the cookie and an optional CSRF token
  (`auth.md`).
- **Keycloak**: `keycloak: { url, realm, clientId, clientSecret, admin }`; users with a `password` get tokens
  (`auth.md`).

What the service talks to:

- **Dependencies** (third parties, sibling services, Kafka, Redis, Toxiproxy): `dependencies:` per environment, each
  with its kind; an HTTP stub carries the provider's vendored contract and the framework refuses any stub that
  contract does not document (`dependencies.md`). Point the backend's provider URLs at the stubs in the stack.
- **Webhooks it receives**: `webhooks:` per environment, with the provider's signing scheme (`webhooks.md`). The
  secret is the same value the backend is given in the stack.

## Rules you can derive

- Headers that the security configuration or framework defaults put on every response (check the configuration,
  then confirm the header name and value with one call: a confirmation, not a source).
- The envelope from the shared response types.
- The datetime offset from the README or the time configuration.
- The stream terminal from the provider style the API mirrors and its docs.
- A response code that only the implementation can produce under a broken environment goes to `coverage.exclude`.

## The stack script

`vgate up|down|status|reset` runs `<svc-dir>/stack.sh`. It sources the library vgate names:

```bash
source "${VGATE_STACK_LIB:?run through vgate: vgate up --service <svc>}"
stack_init <svc>
```

Keep only what is the service's own: its dependencies (`docker compose` with the backend's compose file or the
service's own), the command that starts the app (`app_start <dir> <cmd...>`, which detaches it properly and records
the commit it is built from in `BUILD_REPO`), and the seeding of test data. `STACK_ROOT` is the project.
`example/stack.sh` is the minimal case, `example-orders/stack.sh` one with compose dependencies.

`up` must be idempotent: a stack that is already healthy is left alone, and a fresh database gets the seeded users of
`service.yaml` (`up` on a clean machine must be enough for `gate`). `down` stops without deleting data. `reset` is
destructive and documented as such: it removes test data, keeps migrations and built-in data, and re-seeds the
bootstrap users so the seeded users in `service.yaml` work again.
